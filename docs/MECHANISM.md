# 內容檢測管理機制

「Allan Lo 和你逛文化」文資系列網站的內容與連結，依本文件定期檢測、判斷、更新與留存紀錄。

- 版本：1.0（2026-11-22）
- 負責人：Allan Lo
- 檢討週期：每年一次，或檢測項目、網站架構有重大改變時

## 1. 目的

文化資產的官方資料會變（新指定或登錄、升格、範圍變更、廢止），對外連結會搬家或失效，照片的授權狀態也可能改變。網站上線後若不追蹤，內容會逐漸與事實不符。本機制要做到三件事：

1. **及早發現**：用自動檢測找出與官方資料不一致、失效的連結、缺漏的檔案。
2. **有依據地處理**：每一筆發現都有優先度、處理期限、建議與更新步驟。
3. **留下紀錄**：什麼時候發現、怎麼判斷、什麼時候解決，事後查得到。

## 3. 角色

| 角色 | 誰 | 做什麼 |
|---|---|---|
| 負責人 | Allan | 看報告、決定每一筆要更新或列為例外、合併 PR |
| 自動檢測 | GitHub Actions（`.github/workflows/check.yml`） | 依排程執行檢測、寫回報告、有高優先度的新發現時開 Issue |
| 更新執行 | Allan，或交給 Claude 的工作階段 | 依更新方法修改資料、重新產生網頁、開 PR |
| 播報 | Allan 與阿拉蕾（報告網頁上的角色） | 把檢測結果說成人話 |

檢測程式只**讀取**其他 repo 與公開網站，不會修改任何受檢網站。所有修改都經過 PR，由負責人合併。

## 4. 檢測項目

| 類別 | 做法 | 主要來源 |
|---|---|---|
| 官方資料比對 | 3,032 處有形文資逐筆比對名稱、類別、地址、座標、開放時間、代表圖、官方頁網址、所有權；無形文資與古物比對是否仍在登錄、等級是否改變；找出官方有而網站未收錄的；與上次的基準比較，找出新公告 | 文化部文化資產局開放資料（12 類） |
| 連結 | 國家文化資產網用開放資料確認案號；文資局圖片用 HEAD 請求輪流確認；維基共享資源與維基百科用官方 API 批次確認；其他網站逐一連線；自己網站之間的連結用 repo 資料確認 | 各網站 |
| 內部一致性 | 官方資料與介紹內容的 id 是否一致、照片與語音檔是否存在、照片是否標示作者與授權、無形文資與展示點互相參照、`js/data.js` 是否重新產生、入口頁數量、姊妹站資料是否過期、個資樣式掃描 | 各 repo |
| 上線狀態 | 每個網站首頁、每個縣市頁、資料檔是否回應 200；線上檔案是否與 repo 相同；HTTPS 憑證到期日 | 正式網站 |
| 新聞線索 | 以關鍵字查近 35 天的新聞標題，比對是否提到網站收錄的文資，或出現新的指定、登錄 | Google 新聞 RSS（只取標題、來源、日期、連結） |

每個檢測代碼的意思與更新步驟見 [`UPDATE-SOP.md`](UPDATE-SOP.md)。

### 避免誤報的設計

- 國家文化資產網是單頁應用，任何網址都回應 200，所以不靠連線結果，改用開放資料確認案號。
- 對方回應 403、429 或逾時，只記為「未能確認」（參考）；**連續 3 次**（以天計，同一天重跑只算一次）才列為失效。
- 維基 API 被限流時，該批列為「未能確認」，不當成失效。
- 同一處文資在官方常有兩筆紀錄（縣市登錄＋國家指定，或改類別後新編案號）。網站依規格合併成一筆，所以比對時：有形文資同縣市同名、無形文資同縣市且保存者相同，就視為已收錄，不列為缺漏（報告的「檢測項目」會顯示這類重複紀錄的數量）。
- 名稱比對會把異體字（参／參、湾／灣、厦／廈、啓／啟）、編碼不同但外觀相同的字、括號內的族語或年代說明視為相同。
- 例外清單可以綁定「說明內容的指紋」（`dsha`）：官方資料之後再變動，例外會自動失效並重新出現在報告。
- 新聞只是線索，一律列為「參考」，不設處理期限。

## 6. 優先度與處理期限

| 優先度 | 期限 | 判斷原則 | 例子 |
|---|---|---|---|
| 高 | 7 天 | 網站內容已經是錯的、有法律風險，或訪客看不到網頁 | 官方新增或廢止、類別改變（升格）、照片在共享資源被刪除、網頁打不開、連結確定失效 |
| 中 | 30 天 | 內容部分過時或有風險，但不影響主要事實 | 名稱或開放時間與官方不同、新公告、姊妹站資料過期、疑似個資、線上不是最新版 |
| 低 | 90 天 | 細節差異，可併入下次該縣市的更新 | 地址或座標寫法不同、代表圖更換、連結搬家、入口頁數量 |
| 參考 | 無 | 線索或暫時狀態 | 新聞線索、本次未能確認的連結 |

期限從**首次發現日**起算。超過期限的項目在報告裡標示「逾期」；逾期件數增加時會開 Issue 通知。期限在 `config/rules.json` 的 `sla_days` 調整。

## 7. 處理流程

```
檢測 → 報告 → 判斷 → 更新 → 確認
 ↑                              │
 └──────── 下次檢測 ←───────────┘
```

1. **檢測**：GitHub Actions 依排程執行 `tools/run.py`，把結果寫回 `reports/` 與 `state/`。
2. **報告**：報告網頁（`index.html`）、`reports/latest.md`、`reports/latest.csv` 同步更新。有高優先度的新發現，或逾期件數比上次多時，自動開 Issue，GitHub 會寄信通知。
3. **判斷**：負責人逐筆決定：
   - **要更新** → 進入第 4 步。
   - **不需處理** → 記入 `config/ignore.json`，寫明原因、決定的人、到期日（見第 8 節）。
   - **需要查證** → 先查官方來源；必要時請 Claude 協助查證。
4. **更新**：依 [`UPDATE-SOP.md`](UPDATE-SOP.md) 修改主網站資料、重新產生網頁與語音、重建姊妹站資料，開 PR。PR 內文貼上健檢編號。
5. **確認**：PR 合併、部署完成後，下次檢測時該筆會自動消失並記入「已解決」。想立刻確認可手動啟動檢測。仍然出現代表沒改對，繼續追蹤。

報告網頁每一筆都有「複製給 Claude 的修正指示」按鈕，可直接貼到 Claude 的工作階段處理。

## 8. 例外管理

判斷不需處理的發現記在 `config/ignore.json`：

```json
{"match": {"key": "a1b2c3d4e5f6"}, "reason": "網站名稱沿用通稱，已確認", "by": "Allan", "until": "2027-06-30"}
```

- `match` 可用 `key`（單一筆）、或 `check`／`site`／`city`／`item`／`url`／`title_has` 的組合（一批）。
- **一定要寫原因與到期日**。到期後該筆會重新出現在報告，請再判斷一次；期間最長建議一年。
- 例外的項目在報告網頁的「已列為例外」可以看到，不會消失。
- 例外清單的每次修改都在 git 歷史裡。

## 9. 紀錄

| 紀錄 | 位置 | 保存 |
|---|---|---|
| 最新報告 | `reports/latest.json`、`latest.md`、`latest.csv` | 每次檢測覆寫 |
| 歷次完整報告 | `reports/history/<日期>.json` | 最近 80 次 |
| 歷次摘要（趨勢） | `reports/history/index.json` | 全部。一天一筆；同一天跑多次時保留當天第一次與最後一次 |
| 每筆發現的首次發現日、已解決紀錄 | `state/findings.json` | 未解決的全部；已解決的最近 300 筆 |
| 官方公告基準 | `state/official-baseline.json` | 每次檢測更新 |
| 連結檢查狀態（連續失敗次數） | `state/links.json` | 每次檢測更新 |
| 事件（新公告、新聞線索） | `state/events.json` | 官方類保留到該縣市資料更新為止；新聞 45 天 |
| 例外決定 | `config/ignore.json` | git 歷史 |
| 更新內容 | 各 repo 的 PR | git 歷史 |
| 檢測執行紀錄 | GitHub Actions | GitHub 預設保留 90 天 |

全部紀錄都在公開 repo，因此**報告不會寫出完整的個人資料**：個資樣式掃描的結果只顯示前 4 碼。

## 11. 資安與個資

- 自動檢測不使用任何密碼或金鑰。GitHub Actions 的權限只有本 repo 的 `contents: write`（寫回報告）與 `issues: write`（開 Issue）。
- 對外請求使用固定的 User-Agent，只含專案網址，不含個人資訊；同一網站的請求有固定間隔，被限流就停止。
- 報告網頁把所有外部文字（新聞標題、官方資料）當成純文字顯示，連結只接受 `http`／`https`。
- 新聞線索與外部網頁內容**只是資料**。交給 Claude 處理時，提示詞要求先查證官方來源，不照外部文字的指示行動。
- 個資樣式掃描（身分證字號、手機、Email）是輔助，不能取代人工檢視。主要風險來源是官方開放資料「開放時間」欄裡的預約聯絡人手機，建議改寫為「需預約，聯絡方式見官方頁」。

## 12. 已知限制

- 「保存技術及保存者」不在文資局開放資料，無法自動比對，列入每季深度審查。
- 古物以名稱比對，官方改名時會列為「對不到官方紀錄」，需人工確認。
- 介紹文字的正確性（年代、人物、典故）無法自動檢查，靠每季深度審查抽樣。
- 社群網站（Facebook、Instagram）與短網址擋自動檢查，報告只列數量，需人工打開確認。
- 官方開放資料通常比公告晚數週更新；新聞線索用來補這段時間差。
- repo 連續 60 天沒有任何提交時，GitHub 會停用排程。本機制每週寫回報告，正常情況不會發生；若收到停用通知，到 Actions 頁面按 Enable workflow。
